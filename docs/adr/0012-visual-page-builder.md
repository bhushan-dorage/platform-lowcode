# ADR-0012 — Visual Drag-and-Drop Page Builder

**Status**: Accepted  
**Date**: 2026-07-03  
**Deciders**: Platform Team  

---

## Context

ADR-0010 (Metadata-Driven Page Builder) established that pages are stored as a JSON schema and rendered dynamically — no code deployment required for new screens. ADR-0011 (Claude API for AI-Assisted Page Generation) added a natural-language path to produce those schemas automatically.

However, not all teams can or want to use an LLM:

- Some organisations have **policy restrictions** on sending business prompts to external AI services.
- Small teams or early-stage deployments may have **no budget** for Anthropic API usage.
- Some users prefer **precise, manual control** over every widget and column — the AI can over-produce widgets or choose unexpected layouts.
- The AI generator requires a live internet connection and Anthropic API key configured at the backend; **air-gapped or restricted environments** have neither.

Without a non-AI alternative, these teams would have no way to build pages without custom code, defeating the low-code value proposition.

---

## Options Considered

| Option | Summary | Key Trade-off |
|---|---|---|
| **A. No alternative** | Force all users through the AI generator | Excludes teams with policy/budget/connectivity constraints |
| **B. External page builder** | Embed an open-source builder (GrapeJS, Puck, etc.) | Extra dependency, different schema format, maintenance burden |
| **C. Raw schema editor** | Provide a JSON editor with schema validation | Too technical for Business Analysts — high floor of knowledge required |
| **D. Native visual builder** | Build a three-panel drag-and-drop builder in Studio frontend | Fully owned, same PageSchema output, no external dependency |

---

## Decision

**Build a native visual drag-and-drop Page Builder in `platform-studio-frontend`.**

The builder follows the same three-panel pattern already used by the Form Designer (palette + canvas + editor):

- **Left — Widget Palette**: draggable tiles for all five widget types (KPI, Table, Chart, Form, Text).
- **Centre — Page Canvas**: a live preview of the page under construction. Pages are composed of sections; each section has its own column grid (1–4 columns). Widgets are dropped into sections.
- **Right — Widget Editor**: a properties panel that appears when a widget is selected, with type-specific configuration fields.

### Page key management

The page key (the URL slug) is auto-generated from the page name via `slugify()` while the page has not yet been saved. It becomes locked (read-only) after the first save so the URL never changes unexpectedly.

### Schema format

The builder serialises state to the same `PageSchema` JSON format defined in ADR-0010 and consumed by the AI generator. A page built with the visual builder and a page generated by AI are indistinguishable after saving — both go through `platform-page-service` and render through `PageRenderer` on the portal.

### Save / Publish lifecycle

- **Save Draft** — persists the page as `DRAFT`; not visible to end users.
- **Publish** — transitions the page to `PUBLISHED`; available at `/pages/{pageKey}` on the portal immediately.

---

## Consequences

### Positive

- **No LLM dependency** — works in air-gapped environments with no API keys, no network calls to external services.
- **No additional runtime cost** — page construction happens entirely in the browser; the only backend call is the save/publish request to `platform-page-service`.
- **Full control** — Business Analysts can precisely choose which widgets appear, in which section, in which column order, with exactly the configuration they want.
- **Interoperable output** — pages saved via the visual builder and via the AI generator share the same schema, lifecycle, and renderer. A BA can generate a page with AI and then open it in the visual builder to fine-tune individual widgets.
- **Familiar pattern** — the three-panel layout mirrors the Form Designer already in Studio, so existing Studio users have zero learning curve on the UI chrome.

### Negative / Accepted trade-offs

- **More time to build** — creating a 4-widget page takes more steps than typing a single prompt into the AI generator.
- **BA must know widget types** — the user needs to understand the difference between a KPI, a Table, and a Chart, whereas the AI infers the right type from context.
- **Data source URLs are manual** — unlike the AI generator (which guesses plausible URLs as placeholders), the visual builder requires the user or their platform team to know the correct API endpoint to enter.
- **No AI suggestions** — the builder does not recommend widgets, validate data source URLs, or pre-fill configuration based on the page name.
